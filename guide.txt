🪪 Features to Implement:

✅ Environments
- Isolated environments: dev, staging, prod
- Each with its own backend, provider, state file, and account

✅ Modules
Reusable modules with proper inputs/outputs:
- vpc: AWS VPC, subnets, route tables, IGW, NAT
- eks: AWS EKS cluster, node groups, IAM roles
  - Adds optional Karpenter (on-demand HA) controlled via enable_karpenter variable.
- eks_karpenter: installs Karpenter, configures IAM roles, and sets up two Provisioners:
  - critical: on-demand nodes for workloads labeled workload-type=critical
  - non-critical: prefers spot, falls back to on-demand for workloads labeled workload-type=non-critical
- middleware: managed services like Redis, Kafka, RabbitMQ
- iam: user groups, users, CI/CD least-privilege role, and policy attachments

✅ IAM as Code
- Groups: devops, developers, qa, readonly
- Users: passed as variable maps and assigned to groups
- CI/CD pipeline role with least-privilege policy (policies/ci_cd_pipeline.json)
- Custom policies stored in policies/

✅ Cost-Optimized EKS with Karpenter
- eks module: installs Karpenter for on-demand HA nodes in staging & prod if enable_karpenter=true.
- eks_karpenter module: installs Karpenter for mixed on-demand + spot for cost-optimization.
- Workload scheduling via workload-type labels

✅ Policies
JSON policy files in policies/, e.g.:
- ci_cd_pipeline.json
- eks_read_write.json
- read_only.json

🧠 Cursor AI Prompt

You are tasked with building a Terraform-based Infrastructure as Code repository that provisions a multi-account AWS environment with reusable modules, IAM as code, and cost-optimized EKS with Karpenter autoscaling.

### Additional Requirement:
- In the standard eks module, add optional support for installing Karpenter for on-demand high-availability nodes only, controlled via enable_karpenter variable.
- By default, this is false.
- In staging and prod, it is set to true.
- Create a Karpenter Provisioner in the eks module with:
  - Only on-demand nodes.
  - Balanced across AZs for HA.
  - Labeled for critical workloads.

### Other Requirements:
- Three environments: dev, staging, prod, each fully isolated in its own directory with separate state files and AWS accounts.
- Reusable modules: vpc, eks, eks_karpenter, middleware, iam.
- IAM as code:
  - Groups: devops, developers, qa, readonly
  - Users assigned to groups per environment (via variables)
  - CI/CD IAM role with least-privilege policy from policies/ci_cd_pipeline.json
- Cost-optimized EKS:
  - eks_karpenter module: mixed on-demand + spot
  - eks module: optional Karpenter for HA on-demand
  - Example Kubernetes pod labels to select correct nodes.
- policies/ directory with externalized JSON IAM policies.
- No Terraform workspaces — each environment is a separate directory.
- The repository should follow HashiCorp recommended practices and be future-ready for multi-cloud (GCP, Azure).

### Output:
- Full directory tree.
- Each module scaffold: main.tf, variables.tf, outputs.tf
- Sample policies/*.json files.
- Sample environments/dev/* files instantiating modules.
- README.md explaining setup and usage.



Additional Requirement: GitHub Actions CI/CD Workflows
Add .github/workflows/ directory with three workflow files:

deploy-dev.yml: triggered on push to dev

deploy-staging.yml: triggered on push to staging with manual approval

deploy-prod.yml: triggered on push to main with manual approval

Each workflow must:

Check out code.

Set up Terraform.

Run terraform fmt, validate, plan, and apply against the correct environment directory.

Save the plan as an artifact for review.

Assume the CI/CD IAM role for access.

Use OpenID Connect or AWS secrets securely.

Document the workflow in the README.md file, showing how to trigger each environment deployment and where to view artifacts.
